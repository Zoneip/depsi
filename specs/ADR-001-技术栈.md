# ADR-001 · 技术栈选型

状态：**建议 / 待用户确认**
日期：2026-10-29
关联：`SPEC-001-DepSIPy重实现与优化.md`、`rules/03-数值纪律.md`

## 0. 结论（TL;DR）

| 层 | 选定 | 关键理由 |
| --- | --- | --- |
| 宿主语言 | **Python ≥ 3.11（本机 3.13）** | 与 RapidSAR 干涉链同语言，可直接串起来；生态完整；交接成本低 |
| 数组/线性代数 | **numpy 2.x + scipy 1.1x** | 稀疏法方程、Delaunay、kd-tree、`linalg` 全在 scipy，零额外依赖 |
| 热点加速 | **numba（可选依赖）** | 实测 LAMBDA 逐弧循环 **37×**（97k 弧/s）；纯 Python 兜底保证无 numba 也能跑 |
| 并行 | **numba `prange` + 线程池做 I/O** | 数值核已释放 GIL；I/O 是页缓存/磁盘等待，线程足够，避免进程间大数组拷贝 |
| 稀疏求解 | **`scipy.sparse` + SuperLU（`spla.factorized`）** | 一次因子化、多右端项；解缠正是这个形状 |
| 文件兼容 | **raw 原格式（memmap）+ 原 `param_file.txt`** | 现有工程与 MATLAB 可直接互换；不迁移数据 |
| 工程状态 | **`npz` + `json`（版本化 schema）** | 零依赖、可 mmap；替代 `_project.mat` 的 `save/load/pack` |
| 输出 | **raw（兼容）+ CSV/JSON 报告**；GeoTIFF/图可选 | 主产物要能被原工具链读；报告要人可读 |
| 打包/测试 | **setuptools + pytest**，venv 隔离 | 已是现状，够用 |

明确**不选**：C++/Rust 扩展、Cython、CUDA/cupy、Julia、MATLAB Coder 产物、Dask/Spark。

---

## 1. 背景

需要重实现的是一个**数值密集 + I/O 密集**的批处理程序，特点：

- 单次运行处理 10²–10⁴ 幅 SLC / 干涉图、10⁴–10⁶ 个 PS；raw 数据体量 GB 级。
- 热点是**逐弧标量循环**（LAMBDA 分支定界）与**稀疏最小二乘**。
- 结果是科学量（形变速率、地形、时序），要求可解释、可复现、可对拍。
- 使用者是研究者，环境是 Linux 工作站，无 GPU（本机 16 vCPU / 14 GiB）。
- 已有 Python 干涉链（RapidSAR），希望**同语言打通**。

## 2. 候选与评估

### 2.1 宿主语言

| 方案 | 优点 | 缺点 | 判定 |
| --- | --- | --- | --- |
| **Python + numba** | 与 RapidSAR 同栈；numpy/scipy 覆盖 90% 需求；numba 覆盖剩下 10% 的热点；调试与交接成本最低 | 启动开销、GIL（已用 numba 规避）、类型约束需纪律 | **采用** |
| C++ (pybind11) 重写核心 | 极限性能、内存可控 | 开发/调试/交接成本高；与 Python 链耦合需胶水；本任务瓶颈不在“极限”而在“算法级 I/O 与循环” | 否决（可作后期替换点） |
| Rust | 同上 + 生态更小 | 同上 | 否决 |
| Julia | 数值语言合适 | 与现有 Python 链断裂；团队接手成本；打包分发麻烦 | 否决 |
| 纯 numpy（无 numba） | 依赖最少 | LAMBDA 逐弧循环无法向量化，实测 **37×** 差距，端到端会退化到与 MATLAB 同量级 | 仅作兜底 |

### 2.2 热点加速的具体依据（实测，本机）

```
numba   : 0.206 s / 20000 弧  -> 97,207 弧/s
纯 Python: 7.688 s（外推）     ->  2,601 弧/s
加速比  : 37.4x
```
命令与脚本见 `benchmarks/`（本轮先记录在本 ADR，M4 时脚本化）。

### 2.3 I/O 方案（实测，2000–3000² cpx64）

| 方式 | 耗时 | 说明 |
| --- | --- | --- |
| `freadbk` 式逐行 `seek+read` | 51.2 ms | MATLAB 原实现的方式 |
| 整幅 memmap 读取 | 32.8 ms（**1.6×**） | 页缓存命中时；冷存储差距更大 |
| **稀疏读 1% 像素** | 4.6 ms（**11×**） | 选择步骤的真实用法：只读候选像素 |

结论：真正的加速来自**只读需要的像素**，而不是“换更快的读法”。这是 `steps/selection.py` 的设计前提。

### 2.4 并行模型

| 方案 | 评估 |
| --- | --- |
| **numba `prange`** | 编译期并行，无序列化开销；对 `Narcs×Nifgs` 数组最合适 | **采用** |
| `concurrent.futures.ThreadPool` | I/O 与 scipy 内部释放 GIL 的部分 | 采用（仅 I/O 与少量独立任务） |
| `multiprocessing`/joblib | 大数组要跨进程拷贝；PS 场景内存吃紧 | 否决（除非将来做多项目级并行） |
| Dask/Ray | 过度设计，单机批处理不需要 | 否决 |

### 2.5 稀疏求解

- 解缠法方程 `N = AᵀWA`（`A` 每行两个非零）→ `spla.factorized` 一次，之后每次求解 O(nnz)。
- 备选 dense Cholesky：Npsc 可达 10⁵，稠密不可行，否决。
- 备选 `lsqr`/`lsmr` 迭代：对病态网络收敛慢且精度不可控，保留为 `pinv` 兜底之外的诊断选项。

### 2.6 状态与产物

- 原实现用 `save/load *_project.mat` + `pack`，每组之间整工作区落盘（慢、且 MATLAB 专有）。
- `depsipy` 用 `npz`（数组）+ `json`（元数据、schema 版本、参数快照），目录 `runs/<project_id>/`。
- 兼容层仍写出原 `.raw` 结果文件，供 MATLAB/其他工具读取。

## 3. 后果

**正面**：与 RapidSAR 同语言可直连；numba 覆盖热点；无 GPU 也能跑；依赖只有 numpy/scipy（+可选 numba），安装与交接简单；raw 兼容意味着现有工程零迁移。

**负面 / 代价**：
- numba 与 numpy 版本有耦合（需在 `pyproject` 里给范围并在 CI/文档记录实测组合）。
- 纯 Python 兜底路径慢，必须在文档里讲清「装了 numba 才是标称性能」。
- Python 的启动与包管理对非开发者略重（用 venv + 入口脚本缓解）。

**触发重新评估的条件**：
- 单项目 PS 数 > 10⁶ 且要求分钟级完成 → 需要分块并行或 C++ 核。
- 需要 GPU 批量加速（如大规模周期图/多模型搜索）→ 引入 cupy/torch 分支。
- 目标平台变 Windows/无 numba 受限环境 → 评估 Cython 或纯 numpy 降级策略。

## 4. 验证方式

- 本 ADR 的两组实测数字在 M4 固化为 `benchmarks/run_bench.py` 的可重复输出。
- 每次升级 numpy/scipy/numba 主版本，必须重跑 `pytest` + 基准并把新组合写入 `AGENTS.md`。
